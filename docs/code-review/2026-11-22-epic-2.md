# Epic 2 security and contract review — 2026-11-22

**Release status: NO-GO pending real-stack CI and deployed auth evidence.** The independent reviewer found two deletion blockers in the initial implementation. The implementation leader's follow-up is recorded below; the original findings remain for traceability.

### Follow-up after review

- Confirmation captures the owner and bearer. `delete-account` rejects a verified subject different from `x-confirmed-owner`. Local cleanup conditionally removes only that owner's stored session, never signs out the SDK's current user, and can be retried after a successful remote response. Regression tests cover bearer mismatch and session replacement during cleanup.
- Purge marks the owner retired atomically with deleting progress, preference, cursor and queue. Storage transactions reject later writes and pulls for that owner. Tests cover another IndexedDB connection, late pull, preserved guest rows and rollback. Offline devices not participating in the deletion cannot receive immediate erasure.
- The initial migration limits all client timestamps to the four-digit UTC wire range. No existing hosted database was migrated. The SQL regression rejects year 10000.
- CI now includes Deno handler tests and two browser integrations: public signup/confirmation/recovery through the local mailbox, and two-account offline sync/deletion. These real-stack lanes were not executed on this host. The build is not evidence of Google OAuth or staging deployment.
- For this small beta, the username endpoint keeps its documented shared quota as an abuse ceiling. Email login remains available when that quota is exhausted. Revisit gateway-level throttling before wider rollout.

Scope: the current working tree for R9, R10, and R13, with RLS and integration coverage for progress under R5, R6, R8, and R11. `git rev-parse --verify HEAD` found no baseline. This is a source and test review using differential-review risk and coverage criteria; it cannot establish regressions. I reviewed both migrations, both Edge Functions and their shared HTTP layer, frontend auth and its progress/profile callers, Dexie, the sync adapter and engine, and the workflow and tests. ## Findings

### P1 — Delete confirmation does not bind the account to the request

`frontend/src/pages/AccountPage.tsx:150` renders the confirmation for the UI session. At line 161 it invokes `delete-account` without an explicit bearer; at line 167 it purges the ID captured by the UI, then signs out the SDK's current session. The installed SDK 2.119.2 wires functions to `_getSessionToken()` (`SupabaseClient.ts:380,648`), which reads the shared session when dispatching the request (`lib/fetch.ts:82`). The app stores that session in IndexedDB (`frontend/src/adapters/auth/client.ts:4`), and the SDK notifies other tabs asynchronously (`GoTrueClient.ts:537`). Another tab can replace the stored session before the confirmation tab processes the change. The Edge Function verifies the actual bearer and deletes its subject (`backend/supabase/functions/_shared/delete-account.ts:18,36`). That subject can be account B while the UI confirmed and purged account A. A session change after dispatch can instead make cleanup sign out a newly signed-in account.

Bind confirmation and request to one account. Send the captured bearer, have the server compare the confirmed ID with the verified subject before deletion, and prevent local sign-out from acting on an intervening session. Test session replacement before dispatch and before response. The handler test (`backend/supabase/tests/functions.test.ts:144`) checks bearer identity in isolation; the browser test (`tests/web/accounts.local.spec.ts:55`) covers a stable session.

### P1 — Purge does not fence local writes for the deleted owner

`frontend/src/pages/AccountPage.tsx:166` purges before sign-out. `frontend/src/adapters/auth/AccountProgress.tsx:54` stops sync only on session/effect cleanup, and `frontend/src/core/sync/index.ts:127` can hand a fetched page to storage while deletion is underway. `frontend/src/adapters/local-store/progress.ts:146` deletes rows, outbox entries, and cursors in one transaction, but records no durable retired-owner state. A late first-page pull started with a null cursor can pass the post-purge cursor check and reinsert rows (`frontend/src/adapters/local-store/progress.ts:205`). Another tab that still has the account open can queue an ordinary write after purge (`frontend/src/adapters/local-store/progress.ts:43`). The server cascade cannot remove data resurrected in IndexedDB. Existing tests cover scoped purge and an aborted pull separately (`frontend/src/adapters/local-store/progress.test.ts:64`, `frontend/src/core/sync/sync.test.ts:149`).

Quiesce the owner's sync before purge and enforce a durable owner-retired guard at the local transaction boundary for pulls, writes, and guest merge. Make cleanup retryable if the server has already deleted the account. Test a late first-page pull and a late write from another tab; assert that owner progress, outbox entries, and cursors stay absent. A separate offline device can only react when it reconnects; verify and document that boundary.

### P2 — SQL accepts progress timestamps the client cannot read

All four progress tables accept any finite `timestamptz` (`backend/supabase/migrations/20261122000100_profiles_and_progress.sql:58,68,83,94`), but `frontend/src/core/progress/index.ts:47` requires a four-digit ISO year. An out-of-range year can pass the SQL check and fail row validation in `frontend/src/adapters/supabase-sync/index.ts:165`. That row prevents the pull from committing the page or advancing the cursor; the run exits before it reaches subsequent kinds (`frontend/src/core/sync/index.ts:114`). This affects devices on the same account. The ownership controls prevent ordinary users from inserting it for another account. The SQL test at `backend/supabase/tests/progress.test.sql:40` rejects infinity but does not test the client's accepted range.

Align the SQL and client timestamp domains, define how to repair existing out-of-domain rows, and test accepted and rejected boundaries through PostgREST. Keep the server cursor independent of device clocks.

### P2 — Username login has a shared availability ceiling

`resolve-login` is public (`backend/supabase/config.toml:44`). Accepted lookups, including unknown names, consume a shared allowance before password verification (`backend/supabase/functions/_shared/resolve-login.ts:53`; `backend/supabase/migrations/20261122000200_username_login.sql:22`). Once the bucket fills, legitimate username sign-ins fail until the next five-minute window. Email sign-in follows a separate path. The README documents this tradeoff and pgTAP asserts the cap (`backend/supabase/README.md:13`, `backend/supabase/tests/progress.test.sql:141`).

Rate-limit on trusted gateway/client identity and monitor global saturation. If release accepts the shared ceiling, record the decision and the email workaround. No abuse or load probes were run.

## Evidence and release gates

I found no privileged credential leak in scoped source or a literal secret-pattern scan of the existing build. Verify the actual deployed bundle and key configuration. - **SQL and sync:** Five public tables gate access on `auth.uid()` and confirmed email. The four progress tables use server-owned, per-owner/per-table cursors. The adapter uses the three-column upsert key for state and ignores UUID duplicates for attempts (`frontend/src/adapters/supabase-sync/index.ts:119`). pgTAP asserts cross-owner isolation, write ordering, permissions, and cascades (`backend/supabase/tests/progress.test.sql:25,112,153`). I found no source path for ordinary cross-account progress access. An integration test should verify concurrent server deletion and progress writes leave no rows after a successful delete and handle a retry cleanly.
- **Real CI path:** `.github/workflows/ci.yml:40` starts local Supabase, runs pgTAP, rebuilds with local public config, and opts into the real Playwright account test. The test seeds two confirmed users through the admin API, exercises username and email login, verifies that an offline flashcard write reaches Supabase within the 30-second polling window and becomes visible in a second context, checks another account starts empty, and checks sequential server deletion (`tests/web/accounts.local.spec.ts:24,38,46,55`). Google is disabled locally (`backend/supabase/config.toml:35`), and the Deno handler tests listed in `backend/supabase/README.md:8` are not wired into this workflow.
